## Problem Statement

Hackathon for Good runs twice a year with 15-25 teams per event. The organizer (Martin) currently runs the tech scan manually from his laptop on Sunday morning, converts outputs by hand, and distributes files through multiple channels. Jury members get paper score sheets and 15 minutes of briefing. Challenge owners see submissions for the first time during pitches. Participants get no technical feedback at all unless they make the finals. The organizer cannot be present on the floor because he's the bottleneck for the technical evaluation pipeline.

## What Makes This Cool

An autonomous observatory that watches hackathon submissions from deadline to distribution — scanning code, verifying claims, scoring against the full jury rubric, generating narratives about each team's building journey, and delivering tailored reports to three audiences (jury, challenge owners, participants) through their preferred channels — all without the organizer touching a keyboard. The organizer sets it up once per event and spends Sunday morning with the hackers.

## Constraints

- Python CLI, stdlib + minimal deps (PyYAML, openpyxl, anthropic optional)
- Claude Code CLI or Anthropic API as review backend
- No hosted service — runs on organizer's infra or GitHub Actions
- Junction platform has no score push API; distribution via email/Discord/shared drive
- All repo content is untrusted (prompt injection defense is a hard requirement)
- Must work for HFG first, then generalize via config format
- Budget: weekends over 2-3 months before HFG #9 (May 2027)

## Premises

1. Core value is evidence for human judges, not automated scoring
2. Automation means event-driven triggers (cron/webhook), not a SaaS
3. Junction integration is pull-only; distribution through existing channels
4. Config format IS the generalization — other organizers write their own YAML
5. Multi-criteria scoring requires submission description + challenge brief, not just code

## Cross-Model Perspective

Independent cold read surfaced:

- **Coolest unconsidered version:** Live repo monitoring from first commit — narrative generation ("Team X pivoted to FastAPI at 2am") and cross-team comparison queries ("which teams attempted real-time data ingestion?")
- **Key insight:** The quote "I shouldn't be on my laptop at all" reveals this is about removing the organizer from the critical path, not building a better scanner
- **50% existing:** GitHub analytics API + Semgrep for deterministic scanning; the novel 50% is claim verification, jury pack generation, multi-criteria rubric engine, and platform adapters

## Approaches Considered

### Approach A: Autopilot for HFG (rejected as subset)
Cron trigger + multi-channel distribution. Effort: M. Solves "not on laptop" but stays at 15% of rubric coverage. Built as Phase 1 of the chosen approach.

### Approach B: Full Rubric Scanner (rejected as subset)
Expanded scoring across all jury criteria. Effort: L. Covers 70-80% of rubric. Built as Phase 2 of the chosen approach.

### Approach C: The Observatory (chosen)
Continuous monitoring + narrative generation + full rubric + autopilot. The complete vision.

## Recommended Approach: The Observatory (built in 4 phases)

### Phase 1: Autopilot (2 weekends)

**Trigger system:**
- GitHub Action or Render cron that checks `deadline` from config every 5 minutes
- When deadline passes: pull from Junction (or read local CSV), run full scan, package outputs
- Lockfile prevents double-run; idempotent re-run on failure
- Email output ZIP to configurable recipients (SMTP or SendGrid)

**Distribution layer:**
- PDF per team (already built today with Chrome headless)
- Discord webhook: post summary + per-team scores to a channel
- Shared drive: upload to Google Drive or OneDrive folder via CLI
- Each channel is a pluggable distributor in the config

**Operator runbook:**
- "Running TechScan for HFG without Martin"
- Step-by-step: edit YAML, set env vars, verify cron, interpret output, handle failures
- Troubleshooting guide for common issues (private repos, token expiry, model errors)

**Prompt injection hardening (cross-cutting):**
- Strengthen `extract_json` to prefer `structured_output` over raw text parsing
- Add a second pass that validates the review JSON doesn't contain content from the repo
- Sandbox the LLM: the system prompt explicitly lists which tags are valid; anything else is flagged
- Add a `scan_injection_attempts` check in facts.py that looks for JSON/XML structures in code comments that mimic the review schema
- Log and flag any review where the model's output contains verbatim repo content in unexpected fields

### Phase 2: Full Rubric (2 weekends)

**Multi-criteria scoring:**
- New prompt template that evaluates against configurable criteria (not just tech)
- Default criteria match HFG's rubric: Concept (40%), Prototype (20%), Technology (15%), Potential (15%), Business (5%), Wow (5%)
- Each criterion gets a 1-10 score with evidence and rationale
- Weights are in the YAML config; different hackathons configure different rubrics
- The submission description and challenge brief are first-class inputs alongside code

**Score calibration:**
- Use HFG #8 jury scores (you have them on paper) as ground truth
- Run the expanded scanner on HFG #8 submissions with the new rubric
- Compare AI scores vs jury scores per criterion
- Tune prompts and scoring anchors until correlation improves
- Store calibration data for regression testing

**Wider scale:**
- Move from 1-5 to 1-10 for all criteria
- Add sub-score breakdown visible in the scorecard
- Weighted total matches the jury's formula: A×4 + B×2 + C×1.5 + D×1.5 + E×0.5 + F×0.5

### Phase 3: The Observatory (3-4 weekends)

**Continuous repo monitoring:**
- Polling-based (GitHub API, not webhooks — simpler, no server needed)
- Check registered repos every 30 minutes during the event
- Track: first commit, commit velocity, language additions, file structure evolution, README changes
- Store timeline events in a JSONL file per team

**Narrative generation:**
- After deadline: feed the timeline + final snapshot to the LLM
- Generate a 2-3 paragraph "building journey" narrative per team
- Include: when they started, pivots observed, velocity patterns, team collaboration patterns
- Flag anomalies: sudden large commits, late-night sprints, copied code appearing mid-event

**Cross-team analysis:**
- "Which teams used the challenge data?" (already exists)
- "Which teams attempted real-time features?"
- "Compare the authentication approaches across all teams"
- Query interface: organizer writes a question in the config, scanner answers it across all teams

**Challenge owner report:**
- Separate from the jury pack: focused on "which teams could we work with after this?"
- Highlights: teams that used the challenge data meaningfully, teams with deployed demos, teams with test suites
- Compatibility assessment: tech stack alignment with the challenge owner's org

### Phase 4: Platform adapters + community (ongoing)

**Adapter interface:**
- `list_submissions(config) -> list[Submission]`
- `get_repo_url(submission) -> str`
- `get_submission_text(submission) -> str`
- `distribute(results, channel_config) -> None`
- Junction adapter (exists), DevPost adapter, plain CSV adapter
- Each adapter is a Python file in `adapters/`

**Community packaging:**
- PyPI package (`pip install hfg-techscan` or `pip install hackathon-scanner`)
- GitHub template repo with example config for common setups
- GitHub Action published to the Actions marketplace
- CONTRIBUTING.md with adapter development guide

## Open Questions

1. **Scoring accuracy:** Can an LLM reliably score "Concept" and "Wow factor" from text alone? HFG #8 calibration data will answer this.
2. **Polling rate limits:** GitHub API at 5,000 calls/hour with a token — enough for 25 teams polled every 30 minutes? (Yes: 25 teams × 2 calls × 48 half-hours = 2,400 calls.)
3. **Junction token longevity:** The Clerk `__client` cookie works for days but may rotate. Need to test multi-day persistence or find a service account approach.
4. **Discord distribution:** Bot token vs webhook? Webhook is simpler (no bot framework), but can't DM individual teams.
5. **Narrative quality:** Will 30-minute polling resolution give enough data for interesting narratives, or does it need to be more frequent?

## Success Criteria

- **Phase 1 done:** HFG organizer runs `python -m techscan setup-cron` once, and on event day the scan fires, completes, and emails results without any manual intervention
- **Phase 2 done:** Scanner scores correlate with human jury scores at r > 0.6 across all criteria on HFG #8 calibration data
- **Phase 3 done:** Challenge owners say the building journey narrative told them something they didn't know from the pitch alone
- **Phase 4 done:** At least one non-HFG hackathon has run the scanner using only the README and config template
