## Problem Statement

TechScan works. It scanned 16 teams at HFG #8, produced jury packs that the grand jury used alongside their scoring, and correctly identified the winner. But right now it's one person's tool at one organization's hackathon. The goal is to make it the default technical review tool for hackathons — from school events to corporate innovation days — while keeping it fully open source. HFG offers a managed service ("we run it for your event") as the commercial layer, and the tool plugs into the broader HFG OS "edition in a box."

## What Makes This Cool

The "ESLint for hackathons" — a tool that every hackathon organizer expects to have, the way every JavaScript project expects a linter. Not because someone mandates it, but because once you see the output (claims verified against code, flags for pre-event work, jury questions generated), you can't imagine judging without it. The open-source community contributes adapters for their platform, rubrics for their domain, and translations for their language. HFG runs the managed service for non-technical organizers.

## Constraints

- Must remain fully open source (MIT license, already in place)
- Zero-config for non-technical organizers (via managed service or pre-configured GitHub Action)
- CS students at hackathons must be able to `pip install` and run it
- Plugs into HFG OS as one module
- No budget for infrastructure — GitHub Pages, GitHub Actions, free-tier services only
- Martin can't be the bottleneck — community must be self-sustaining

## Premises

1. The open source project's job is adoption, not revenue
2. The README is the product for the open source community
3. Adapters are the community contribution surface
4. The zero-config version is a hosted service, not a smarter CLI
5. Both PyPI and HFG OS are distribution channels (CS students + organizers)

## Approaches Considered

### Approach A: Developer-First README
Just nail the README and docs. Rejected: necessary but not sufficient.

### Approach B: Showcase + Contribute
Live showcase + contributor on-ramp. Rejected: a good step but doesn't build the ecosystem.

### Approach C: Open-Core Ecosystem (chosen)
Full ecosystem: showcase, GitHub Action, rubric marketplace, event leaderboard, community.

## Recommended Approach: Open-Core Ecosystem

Build in three waves, each shippable independently:

### Wave 1: The Showcase (1 weekend)

**The README** — modeled after the best open-source READMEs (FastAPI, Ruff, Gavel):
- Hero: one-sentence value prop + a GIF or screenshot of the jury pack output
- "Try it in 2 minutes" quick start with `demo` + `selftest` commands
- Live demo link (GitHub Pages hosting the HFG #8 jury pack HTML)
- Badges: Python version, license, tests passing, PyPI version
- Clear sections: What it does, How it works (with diagram), Quick start, Configuration, For organizers, For contributors
- "Used at" section with HFG #8 logo + stats (16 teams, 216K lines, 19 minutes)

**GitHub Pages showcase** at `hackathon-for-good-the-hague.github.io/hfg-techscan`:
- Host the HFG #8 `jury-pack-all.html` as a live demo
- Landing page: "See what TechScan produces" → click to browse real output
- Anonymize team names if needed, or get consent from HFG #8 participants

**Social proof seed:**
- Post in MLH organizer communities
- Post in Junction community Discord
- Share with HFG's existing school/MBO network
- Tweet thread: "We built an AI that reviews hackathon code and it found things 3 jury members missed"

### Wave 2: The Contributor Flywheel (2 weekends)

**"Good first issues" for adapters:**
- Issue template: "Add [Platform] adapter" with step-by-step instructions
- Bounty labels: `good-first-issue`, `adapter-wanted`, `help-wanted`
- Platforms to target: DevPost (adapter exists), Luma, Eventbrite, MLH, HackerEarth, Unstop
- Each adapter is ~50-100 lines following a clear interface

**Rubric library** (`rubrics/` directory):
- `rubrics/hfg-regular.yaml` — the HFG grand jury rubric (already exists as config)
- `rubrics/mlh-default.yaml` — MLH's standard 4 criteria
- `rubrics/ethglobal.yaml` — ETHGlobal's criteria
- `rubrics/school-simple.yaml` — simplified 3-criterion rubric for school events
- Community contributes their own; PR template includes the rubric + a description of when to use it

**GitHub Discussions** (not Discord — lower friction, lives in the repo):
- Categories: Show & Tell (post your event's results), Rubrics (share configs), Adapters (development), Feature Requests
- Pin: "Share your hackathon's TechScan results" thread

**CONTRIBUTING.md upgrade:**
- "Your first contribution" walkthrough (fork → write adapter → test with demo → PR)
- Architecture diagram showing where adapters, rubrics, and checks plug in
- Code of conduct (already have it via template repos)

### Wave 3: The Ecosystem (1 month)

**GitHub Action on the Marketplace:**
- `uses: Hackathon-for-Good-The-Hague/hfg-techscan@v1`
- Inputs: config path, submissions CSV, API key
- Outputs: scorecard + jury packs as artifacts
- Zero-install: works on any repo, any hackathon
- README example: "Add this to your hackathon's `.github/workflows/`"

**Event leaderboard** (GitHub Pages, static):
- JSON file in the repo: `events.json` with name, date, teams, link to results
- PR to add your event (like "awesome-" lists)
- GitHub Pages renders a simple page: "TechScan has been used at X events, reviewing Y teams"
- Social proof flywheel: organizers want to be on the list

**Rubric analytics:**
- After enough events: "The most used rubric is X" / "Events with rubric X have higher score spread"
- Published as a blog post or GitHub Discussion — content that drives discovery

**Translations:**
- The jury pack HTML and PDF output support i18n
- Community contributes Dutch, French, Spanish, Arabic translations
- School hackathons in non-English countries can use it immediately

## Open Questions

1. **Anonymization**: Can we host HFG #8 results publicly? Need consent from teams, or anonymize names.
2. **Managed service pricing**: What does HFG charge when running TechScan for a client event? Per-event? Per-team? Included in edition-in-a-box?
3. **Community moderation**: Who reviews rubric PRs and adapter PRs? Need at least 2 maintainers.
4. **API key distribution**: CS students using Claude need an API key. Does HFG provide a shared key for open-source users, or do they bring their own?

## What I noticed about how you think

- You said "it needs to remain open source" without hesitation, but immediately followed with "we can run it for them as a service." You instinctively see the WordPress model — give the engine away, charge for the hosting. That's one of the strongest open-source business models and you landed on it in one sentence.
- You mentioned "edition in a box" and "HFG OS" as if they're obvious — you're already thinking at the ecosystem level, not the tool level. TechScan is one module in a larger vision. That framing is what makes the open-source pitch compelling: you're not asking people to adopt a scanner, you're inviting them into a movement for better hackathons.
- You said "even small organizers use this for their school hackathons." That's the wedge that makes open source work — the users with the least resources get the most value from a free tool. They'll never pay, but they'll tell everyone about it.
- When I asked about the fastest path, you said "it needs to be automatic from their event start." You keep coming back to the same principle: the organizer should be with the hackers, not at a laptop. That's not a feature request — it's a design philosophy that should be in the README's first paragraph.
