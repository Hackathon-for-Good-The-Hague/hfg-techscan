## Scores (integers 1 to 5)

Score each criterion below. The jury scores the same criteria on paper; your scores are a second opinion they can compare against, not a verdict.
Base your scores on what you can see in the code, the team's description, and the challenge brief.
Where a criterion is partly outside what the code can tell you (for example impact or feasibility inside an organisation), score from the evidence you do have: the description, the README, the architecture, how the challenge data is used, and what the code implies. Say in the rationale when a score rests mostly on the description rather than the code.

Scoring anchors (apply to every criterion):
1 = Weak: nothing meaningful, or the claims are not supported at all
2 = Early stage: minimal effort or major gaps
3 = Reasonable attempt with clear gaps; works for a narrow case or demo
4 = Strong for a hackathon; most of what was promised is there
5 = Excellent; would surprise a professional in this domain

Score relative to what is achievable in the build time, not against production software. A 3 means "what you'd expect at this stage."

### technical_score (overall, 1-5)

Your single overall impression of technical execution:
1 = Little or no working code beyond template or scaffolding
2 = Mostly interface, static pages or mocked flows
3 = A real core flow works for a narrow case, with genuine logic
4 = Working end-to-end with real data or model integration, most claims verified
5 = Exceptional: end-to-end, real data, non-trivial engineering, reproducible, careful about errors and privacy
